# 拦截和异常

根据前面的文档与日常开发规范，对**拦截**与**异常处理**核心知识总结如下：



### 一、 核心概念与作用

| **维度**     | **拦截机制（Interceptor / Filter）**                         | **异常处理机制（Exception Handling）**                       |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **核心目的** | **安全防护与统一网关**：在请求到达 Controller 之前统一进行身份认证、权限校验、日志记录等。 | **统一兜底与友好响应**：捕获程序运行中抛出的错误，屏蔽底层的崩溃堆栈信息，向前端返回标准化 JSON。 |
| **触发时机** | **前置拦截**：请求进入 Controller 处理**之前**。             | **后置捕获**：Controller 或 Service 层代码**抛出异常时**触发。 |
| **典型场景** | 未登录拦截（如拦截 `/user/**`）、权限控制、Token 校验。      | 参数校验失败（`MethodArgumentNotValidException`）、业务规则不符（如“余额不足”）、系统崩溃（`Exception` 兜底）。 |

### 二、 拦截机制（Interceptor）总结

1. **核心组件**：
   - **`LoginProtectInterceptor`**：实现 `HandlerInterceptor` 接口，在 `preHandle` 方法中获取 Session 或 Token。若未登录，通过 `HttpServletResponse` 手动写回 `code: 401/501` 的 JSON 响应并返回 `false` 终止请求。  
   - **`WebMvcInterceptorConfig`**：加上 `@Configuration` 并实现 `WebMvcConfigurer` 接口。通过 `addInterceptors` 注册拦截器，并用 `addPathPatterns` 配置拦截路径（如 `/user/**`），用 `excludePathPatterns` 配置放行路径（如 `/auth/login`、静态资源）。  
2. **拦截器（Interceptor）与过滤器（Filter）的核心区别**：  
   - **工作平台**：Filter 工作在 Servlet 容器层面（所有 Java Web 项目通用）；Interceptor 基于 Spring MVC 框架。  
   - **配置灵活性**：Filter 只能配置拦截地址，不能配置放行地址；Interceptor 既可配置拦截路径，也可配置排除放行路径。  

### 三、 异常处理机制（Exception Handling）总结

1. **核心组件**：
   - **`GlobalExceptionHandler`**：使用 `@RestControllerAdvice` 标注此类为全局异常处理器（类中方法默认返回 JSON）。  
   - **`@ExceptionHandler(XxxException.class)`**：标注在方法上，精准匹配并处理指定类型的异常。  
2. **常用的三种异常拦截策略**：
   - **参数校验异常**：拦截 `@Valid` / `@Validated` 触发的 `MethodArgumentNotValidException`，从 `BindingResult` 中提取字段错误原因，拼装后返回。  
   - **自定义业务异常**：创建继承 `RuntimeException` 的 `BusinessException`。业务代码中出现非法逻辑（如账号已存在）时直接 `throw new BusinessException("错误提示")`，由全局处理器精准捕获并输出提示。  
   - **系统兜底异常**：捕获最高父类 `Exception.class`，在日志中记录原始报错堆栈，同时给前端返回统一的“服务器繁忙，请稍后再试”。  

### 四、 两者结合的日常开发标准流向

在优雅的后端架构中，两者的协同运行流程如下：

Plaintext

```
客户端请求 (Request)
      │
      ▼
【拦截器 Interceptor】──(未登录/无权限)──► 拦截并直接输出 JSON (Code: 401/501)
      │
      │ (已登录放行)
      ▼
【表现层 Controller】──(参数非法)──► 抛出 Validation 异常 ──┐
      │                                                │
      ▼                                                │
【业务层 Service】───(业务逻辑冲突)──► 抛出 BusinessException ─┼──► 【全局异常处理器】
      │                                                │     @RestControllerAdvice
      ▼                                                │     捕获异常并统一打包为 Result(JSON)
【数据层 DAO/数据库】──(代码崩溃/空指针)──► 抛出 System Exception ──┘
```





在日常开发中，**统一异常处理**和**登录/权限拦截**是 Spring Boot 项目的最基础规范。标准的做法是：**不在业务代码（Service/Controller）中到处写 `try-catch`**，而是让异常向上抛出，由全局异常处理器统一捕获，并配合拦截器实现敏感接口的保护。

### 一、 统一异常处理写法

#### 1. 定义全局异常处理器（`GlobalExceptionHandler`）

在项目中创建一个专门处理异常的类，加上 `@RestControllerAdvice` 注解。



Java

```
package com.example.exception;

import com.example.utils.Result;
import org.springframework.validation.BindingResult;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.stream.Collectors;

/**
 * 全局异常处理器
 * 作用：统一捕获 Controller 抛出的异常，返回标准 JSON，避免将后端报错堆栈泄露给前端
 */
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 1. 拦截参数校验异常（@Valid / @Validated 校验失败时抛出）
     */
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public Result handleValidationException(MethodArgumentNotValidException e) {
        BindingResult bindingResult = e.getBindingResult();
        // 拼接所有属性的错误提示信息（如："用户名不能为空；手机号格式错误"）
        String errorMsg = bindingResult.getFieldErrors().stream()
                .map(error -> error.getField() + "：" + error.getDefaultMessage())
                .collect(Collectors.joining("；"));
        return Result.fail(400, "参数校验失败：" + errorMsg);
    }

    /**
     * 2. 拦截自定义业务异常（如：账号已存在、余额不足等）
     */
    @ExceptionHandler(BusinessException.class)
    public Result handleBusinessException(BusinessException e) {
        return Result.fail(e.getCode(), e.getMessage());
    }

    /**
     * 3. 兜底处理所有未预料到的系统异常（如：空指针、数据库连接失败、除零错误等）
     */
    @ExceptionHandler(Exception.class)
    public Result handleException(Exception e) {
        // 生产环境中在此处用日志工具记录详细堆栈：log.error("系统异常", e);
        e.printStackTrace(); 
        return Result.fail(500, "服务器繁忙，请稍后再试");
    }
}
```

#### 2. 自定义业务异常类（`BusinessException`）

便于在业务逻辑中随时 `throw` 终止程序并给前端提示：



Java

```
package com.example.exception;

import lombok.Getter;

/**
 * 自定义业务异常
 */
@Getter
public class BusinessException extends RuntimeException {
    private final Integer code;

    public BusinessException(String message) {
        super(message);
        this.code = 500;
    }

    public BusinessException(Integer code, String message) {
        super(message);
        this.code = code;
    }
}
```

#### 3. 业务代码中的实际使用方式

在 Service 或 Controller 中，出现不合规逻辑时**直接抛出异常**即可：



Java

```
@Service
public class UserServiceImpl implements UserService {

    @Autowired
    private UserDao userDao;

    @Override
    public void register(UserDTO userDTO) {
        // 校验账号是否已存在
        if (userDao.findByUsername(userDTO.getUsername()) != null) {
            // 直接抛出业务异常，GlobalExceptionHandler 会自动捕获并返回 {code: 500, message: "用户名已存在"}
            throw new BusinessException("用户名已存在");
        }
        // 正常保存逻辑...
    }
}
```

### 二、 拦截器（Interceptor）写法

日常开发最常见的场景就是**登录保护拦截**：拦截未登录用户的请求，放行公共资源。



#### 1. 编写拦截器类（`LoginProtectInterceptor`）

实现 `HandlerInterceptor` 接口，在请求进入 Controller 前做校验：



Java

```
package com.example.interceptor;

import com.example.utils.Result;
import com.fasterxml.jackson.databind.ObjectMapper;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;
import org.springframework.stereotype.Component;
import org.springframework.web.servlet.HandlerInterceptor;

import java.io.PrintWriter;

/**
 * 登录保护拦截器
 */
@Component
public class LoginProtectInterceptor implements HandlerInterceptor {

    private static final ObjectMapper objectMapper = new ObjectMapper();

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) throws Exception {
        // 1. 获取 Session（如果是 Token 验证，则在此处获取 Header 中的 Authorization 校验）
        HttpSession session = request.getSession();
        String username = (String) session.getAttribute("username");

        // 2. 如果未登录，拦截并手动输出 JSON 给前端
        if (username == null || username.isEmpty()) {
            response.setContentType("application/json;charset=UTF-8");
            
            // 约定的未登录状态码（如 401 或 501，引导前端跳转到 login.html）
            Result errorResult = Result.fail(401, "未登录，请先登录！");
            
            PrintWriter writer = response.getWriter();
            writer.write(objectMapper.writeValueAsString(errorResult));
            writer.flush();
            writer.close();
            
            return false; // 返回 false 表示拦截，不再进入 Controller
        }

        // 3. 已登录，返回 true 放行
        return true;
    }
}
```

#### 2. 配置并注册拦截器（`WebMvcInterceptorConfig`）

创建一个配置类实现 `WebMvcConfigurer`，配置拦截规则与放行规则：



Java

```
package com.example.config;

import com.example.interceptor.LoginProtectInterceptor;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

/**
 * Web MVC 配置类
 */
@Configuration
public class WebMvcInterceptorConfig implements WebMvcConfigurer {

    @Autowired
    private LoginProtectInterceptor loginProtectInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginProtectInterceptor)
                // 设置需要拦截的路径（拦截所有以 /user 开头的请求）
                .addPathPatterns("/user/**")
                // 设置放行的路径（放行登录、注册接口及前端静态资源）
                .excludePathPatterns(
                        "/auth/login",
                        "/auth/register",
                        "/*.html",
                        "/*.css",
                        "/*.js",
                        "/images/**"
                );
    }
}
```

### 三、 日常开发套路总结

1. **控制器层 (Controller)**：只负责使用 `@Valid` 接收和触发校验，无需处理 `try-catch` 或登录判断。
2. **业务逻辑层 (Service)**：专注业务流转，发现条件不符直接 `throw new BusinessException("错误原因")`。
3. **全局异常层 (GlobalExceptionHandler)**：负责全局兜底，自动将所有抛出的异常转换为统一的 `Result.fail(...)` 返回给前端。
4. **拦截器层 (Interceptor)**：拦截非法请求（如未登录、无 Token），拦截后直接回写 JSON 提示 `401/501` 促使前端重定向。

以下是关于 **Spring MVC 拦截器（HandlerInterceptor）** 的核心知识点总结：



### 一、 拦截器的基本概念与作用

1. **定义**：拦截器是 Spring MVC 框架提供的一种声明式 AOP（面向切面编程）机制。  
2. **核心作用**：在请求到达 Controller（Handler）之前或之后，对请求进行统一的前置/后置处理，避免在每个 Controller 中编写重复的代码。  
3. **常见应用场景**：
   - **身份认证/登录保护**（如未登录拦截并重定向到登录页或返回 `401/501`）。  
   - **权限控制**（检查当前登录用户是否拥有操作权限）。
   - **全局日志记录**（记录请求 URL、IP 地址、耗时等）。
   - **性能监控**（记录接口处理耗时）。

### 二、 拦截器的三大生命周期方法

拦截器类需实现 `HandlerInterceptor` 接口，重写以下三个方法（根据需求按需重写）：



| **方法名**              | **触发时机**                                                 | **核心作用与返回值**                                         |
| ----------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **`preHandle()`**       | 目标 Controller 方法执行**之前**。                           | **前置拦截**。返回值：  • `true`：放行，继续执行后续拦截器或 Controller；    • `false`：拦截，中断请求执行（后续代码及 Controller 均不执行，需在此方法内手动回写响应数据）。 |
| **`postHandle()`**      | Controller 方法执行完毕**之后**，且在视图渲染**之前**。      | **后置处理**。可对 Controller 返回的 `ModelAndView` 或响应数据进行二次修改。注意：若 Controller 加了 `@ResponseBody`，响应数据已写入输出流，此时修改数据无效。 |
| **`afterCompletion()`** | 整个请求完全处理完毕（视图渲染完成或 JSON 响应已输出）**之后**。 | **资源清理/收尾**。无论成功还是抛出异常均会触发，常用于清理上下文资源（如 ThreadLocal）、释放数据库连接或计算接口总耗时。 |

### 三、 拦截器的注册与匹配规则配置

实现拦截器类后，必须将其注册到 Spring MVC 的配置类中才能生效。  



#### 1. 配置步骤

1. 编写拦截器实现类（加上 `@Component` 纳入容器）。  
2. 编写配置类，加上 **`@Configuration`** 注解，并实现 **`WebMvcConfigurer`** 接口。  
3. 重写 **`addInterceptors()`** 方法进行注册。  

#### 2. 路径匹配语法（AntPathMatcher）

- **精准匹配**：`/user/login`

    

- **单层模糊匹配 (`\*`)**：`/user/*`（可匹配 `/user/add`，但不能匹配 `/user/add/detail`）  

- **多层模糊匹配 (`\**`)**：`/user/**`（可匹配 `/user` 目录下的任意多层级路径）  

#### 3. 配置方式示例

Java

```
@Configuration
public class WebMvcInterceptorConfig implements WebMvcConfigurer {

    @Autowired
    private LoginProtectInterceptor loginProtectInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(loginProtectInterceptor)
                .addPathPatterns("/user/**") // 配置拦截路径
                .excludePathPatterns(        // 配置放行路径（排除特定接口与静态资源）
                        "/auth/login", 
                        "/auth/logout", 
                        "/*.html", 
                        "/*.css", 
                        "/*.js"
                )
                .order(1); // 手动设置多个拦截器的执行顺序，数值越小优先级越高
    }
}
```

### 四、 多个拦截器的执行顺序

当一个请求匹配到多个拦截器时，执行链遵从“**先进后出**”（类似栈）的原则：  



1. **正常放行情况**：
   - 所有拦截器的 `preHandle()` 依次**正序**执行（1 ➔ 2 ➔ 3）。  
   - 执行目标 Controller 方法。  
   - 所有拦截器的 `postHandle()` 依次**倒序**执行（3 ➔ 2 ➔ 1）。  
   - 所有拦截器的 `afterCompletion()` 依次**倒序**执行（3 ➔ 2 ➔ 1）。  
2. **中途拦截情况**（如第 2 个拦截器的 `preHandle()` 返回 `false`）：  
   - 拦截器 1 和 2 的 `preHandle()` 正常执行，拦截器 3 不执行。  
   - **Controller 不会执行**。  
   - 所有拦截器的 `postHandle()` **均不执行**。  
   - 已放行的拦截器 1 的 `afterCompletion()` 会执行（用于清理之前建立的资源），拦截器 2 和 3 的 `afterCompletion()` 不执行。  

### 五、 拦截器（Interceptor）与 过滤器（Filter）的对比（高频面试点）

| **对比维度**          | **过滤器 (Filter)**                                          | **拦截器 (Interceptor)**                                     |
| --------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **依赖技术/工作平台** | 基于 **Servlet 规范**，依赖于 Servlet 容器（如 Tomcat），适用于所有 Java Web 项目。 | 基于 **Spring MVC 框架**，属于 Spring 框架自身特有的 AOP 机制。 |
| **作用范围/拦截粒度** | 能够拦截发送给 **Servlet 容器**的所有请求（包含 JSP、HTML、图片等任意静态资源）。 | 仅拦截发送给 **Spring MVC 核心控制器（DispatcherServlet）** 处理的请求。 |
| **容器组件调用**      | 无法直接使用 Spring 容器中的依赖注入（如 `@Autowired` 获取 Bean 比较麻烦）。 | 本身就是 Spring 容器中的 Bean，可以**自由使用 `@Autowired` 注入**其他 Service 或 Component。 |
| **配置灵活性**        | **只能配置拦截路径**，不能在配置中直接指定排除放行路径。     | 既可配置**拦截路径** (`addPathPatterns`)，也可配置**放行路径** (`excludePathPatterns`)[cite: 2]。 |
| **执行时机**          | 请求进入 Servlet 容器后，进入 DispatcherServlet **之前**触发。 | 请求进入 DispatcherServlet 之后，到达 Controller **之前**触发[cite: 2]。 |

> **选型建议**：在 Spring Boot / Spring MVC 项目中，若要实现业务相关的身份校验、登录保护或接口耗时统计，**优先选用拦截器（Interceptor）**[cite: 2]。
